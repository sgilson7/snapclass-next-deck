SnapClass Next: how it is built, and how we will work in it

SnapClass has grown for about ten years, and its architecture now limits what we can add to it. SnapClass Next rebuilds it as a protected core of small services plus mods, and it runs today on Docker Compose and on Kubernetes.

By the end you should be able to explain what a microservice is, why large online services are built that way, and what writing, testing, reviewing and releasing code for SnapClass will look like.

Ten years, many developers, one shared codebase

  • Many developers have added to SnapClass over about ten years, each working toward their own feature or study. The architecture never said where a study's code should go, so each one went where it fit at the time: a route folder, a table, a patch to Snap.
  • Each choice was reasonable when it was made. Together they put every feature in the same process, the same database and the same deploy, so a change anywhere can affect everything.
  • The team has already put rules around this: feature branches merged into dev by pull request, one approving review, 4 required check workflows, and a typed authorization layer over 130 operations. The rework keeps those practices and changes the structure underneath them.

What that costs: one new feature touches 17 shared places

  • The test case: a panel beside Snap that shows a student's scripts as Python-like text and lets them edit it. On SnapClass today it changes 17 places in shared code, and shipping it restarts SnapClass for every class.
  • Growth is limited by that: every study adds risk for every other class, and two teams cannot change their features independently. Press Play on What has to change.
background the vocabulary

Microservices in one slide

  • A microservice is a small program that does one job, owns its own data, and is deployed on its own. Other services reach it only through its published contract: HTTP requests, or events on a queue.

A monolith (SnapClass today)

  • One codebase, one process, one database
  • Features call each other as functions and share tables
  • One deploy ships every feature at once
  • Scales by running a bigger machine
  • Simple to start; harder to change safely as it grows

Microservices (SnapClass Next)

  • Each service owns one job and one database schema
  • Services talk through HTTP contracts and events
  • Each service is built, tested and deployed on its own
  • Scales by running more copies of the busy service
  • More moving parts, so testing, deploys and monitoring are automated

Gateway

The one door from the internet. It checks the sign-in token and routes each request to a service.

Container image

A service and everything it needs, built once and run the same on a laptop and in prod.

Kubernetes

Runs the containers: several copies of each, restarted when one fails, updated one copy at a time.

202 and a worker

Slow work is accepted at once (202 Accepted) and done later by a worker reading a queue.

background with sources

Why large online services are built this way

Ship one part at a time

A fix to grading ships without restarting sign-in. Small releases are easier to test and to roll back.

Scale the busy part

At the start of a lab, saving work is busy and grading is quiet. Add copies of the work service only.

Contain failures

A service that fails takes its own feature down, not the site. In SnapClass Next a broken mod leaves Snap, saving and grading working.

Teams own services

A team reviews and ships its own service. Conway observed that a system's structure mirrors the teams that build it, so the structure is chosen to match the teams.

  • Cloud platforms and Kubernetes are designed around one container per service, and Microsoft's Azure Architecture Center describes microservices as one of its standard architecture styles.
  • They have real costs: more pieces to run, calls over the network that can fail, and data spread over several stores. Fowler's advice is to start with a monolith and split it once its seams are known. After ten years, SnapClass's seams are known; slides 11 to 13 cover the automation that pays for the extra pieces.

Sources: J. Lewis and M. Fowler, Microservices (2014); M. Fowler, MonolithFirst (2015); M. Conway, How Do Committees Invent? (1968); Microsoft, Microservices architecture style and Asynchronous Request-Reply pattern; Kubernetes overview.

measured running today, traced from its code

SnapClass Next: 6 core services, 5 mods, one gateway

  • The core is identity (sign-in), course, work (saving, submitting, grading), registry (which mods are on where), telemetry (the research trace) and the gateway. Each service has its own database schema and its own database user, so one service cannot read another's tables.
  • Mods run in their own containers: a water simulation, a shell view, struggle detection, an AI tutor and an answer guard. They reach the core only through 10 published extension points.
  • Press Play on a flow: a Snap block drives the simulation in the mod's container, and its state streams back to the browser.

measured the mod contract · proposed who owns what

A core team owns the core; everyone else writes mods

The core team

  • The only people who change services/, packages/, web/ and deploy/
  • Review every core pull request; GitHub enforces it with CODEOWNERS
  • Keep the 10 extension points stable and versioned, so a mod written this year still loads next year
  • Run the releases

Mod developers

  • Research projects, students and other teams
  • Write a mod in its own repository: a manifest, a container, its own data
  • Use only the extension points: host API in Snap, a panel beside Snap, routes under /mods/<name>/, events
  • Sideload it: install from its manifest, an admin approves the version, a teacher turns it on per section
  • The core is what every class depends on, so it changes slowly, through a small team with a high bar. Mods are where research moves fast, and a mod that fails takes down only itself.
  • Today the 5 mods still live in the SnapClass Next repository under mods/. Separate repositories and installing a mod without touching the core are the next step, and still a proposal.

Writing new code: a mod, from manifest to panel

  1. A manifest (mod.json) says what the mod adds and which host API version it needs.
  2. A service in its own container answers under /mods/<name>/api/. The gateway checks the token and that the mod is on for the student's section.
  3. A Snap script uses the host API: defineBlocks, call, subscribe, onActivity.
  4. A panel beside Snap runs in a sandboxed frame and talks to the page through the bridge.
  5. Tests: unit tests, and a system test plan for the student's flow.

Testing that proves itself

Unit and contract

229 tests

One function or one service's API, in milliseconds. Contract tests check that a service's requests and events match what others expect.

System test plans

18 plans

97 tests that follow a user's flow in a real browser against a deployed copy: sign in, open an assignment, save, submit, grade.

Break tests

76 bugs

Each plants one bug in the source and passes only if the tests named for it fail. A test that cannot fail proves nothing.

  • A bug fix comes with a test that fails without the fix. This week the health monitor kept an old incident open: a test reproduced it, putting the bug back made that test fail (break B76), and then the fix went in.
  • Each unit test is listed under the system test step that needs it, so a failing test points at the user's flow it protects.
measured the release script, step by step

One command takes a commit to prod, or stops

  • Nobody deploys by hand. One script builds the images, deploys them to smoke, runs every system test plan and the reliability gate there, and only then gives prod the same image tag.
  • It runs on a laptop today. On GitHub the same script becomes the job that runs after a merge to main, so continuous integration (the checks on every pull request) and continuous delivery (this release) use the same steps.
measured how SnapClass Next releases · background with sources

Why every release goes to smoke before prod

  • Unit tests check code on its own. Many failures appear only when the services run together: a missing setting or secret, a database migration, a wrong address between services, a memory limit, or load.
  • Smoke is a full copy of prod with synthetic classes: the same images, the same Kubernetes files and the same limits. A release that works there has been rehearsed, and no student sees a release that failed.
  • Prod gets the exact image tag that passed, never a rebuild, so what students run is what was tested. A failed release leaves prod on the version it had.
  • This is the same idea as testing dev before main today, made automatic. Large services go further and release to a small group of real users first, a canary, then widen it.

Working in the repository: a branch per feature, a pull request per milestone, a commit per change

  • A branch per feature, as today. A feature starts as a short spec that splits it into milestones.
  • A pull request per milestone, small enough to review in one sitting. Each one names the spec, the milestone and its tests, and can ship on its own.
  • A commit per logical change, written for the person reviewing it: it builds and passes its tests on its own, and its message says what changed and why. A reviewer can then read the pull request one commit at a time.
  • What changes from today: core paths need the core team's review, mods are reviewed by their own team, and the smoke copy does the system testing dev gets by hand. Whether we still need a long-lived dev branch is for us to decide.

Source: GitHub Docs, About code owners.

example one pull request, two attempts

Example: the same work, restructured into commits a reviewer can follow

  • A developer builds milestone M1 of help requests: a function that checks a request, the route that calls it, and a system test. The code is the same in both attempts. Only the commits differ.

First attempt: grouped by bedtime

  1. wip help requests11:48 pm
    • course/src/help.ts half written
    • course/src/app.ts the route, calling it
    • course/test/help.test.ts two of the tests
    • system/stp-19-help.spec.ts started

    Does not pass its tests: the developer committed before bed.

  2. finish help requestsnext day, 10:15 am
    • course/src/help.ts finished, and renamed a field the route used
    • course/src/app.ts fixed to match
    • course/test/*.test.ts the remaining tests
    • system/stp-19-help.spec.ts finished

The reviewer has to read both commits at once to see what any one piece does, and cannot tell which test covers which change.

Second attempt: one logical change per commit

  1. course: helpRequestFrom() checks and builds a help request
    • course/src/help.ts the function
    • course/test/help.test.ts a test for each rule: an empty message is refused (U-course-14), a student outside the section is refused (U-course-15), a long message is trimmed (U-course-16)
  2. course: POST /help answers 202 and publishes help.requested
    • course/src/app.ts the route, which calls helpRequestFrom()
    • course/test/app.test.ts answers 202 and publishes the event (U-course-17); a refused request comes back as 400 (U-course-18)
  3. system: STP-19 a student asks for help and the teacher sees it
    • system/stp-19-help.spec.ts end to end in a browser
    • docs/SYSTEM-TESTS.md the plan's steps

Each commit builds and passes its tests on its own. The reviewer checks the function, then the wiring, then the behaviour.

How to restructure it

  1. Undo the two commits but keep the work: git reset --soft to where the branch started, then unstage everything.
  2. Stage one logical change at a time, with its tests, and commit it. git add -p stages part of a file, which helps when app.ts holds changes for two commits.
  3. Prove each commit passes on its own: git rebase --exec runs the tests after every commit.
  4. Update the pull request with --force-with-lease, which refuses if someone else pushed to the branch meanwhile. Rewrite only your own feature branch, never main.
git switch feat/help-requests
git reset --soft "$(git merge-base origin/main HEAD)"   # where the branch started:
                                  # keep the work, drop the 2 commits
git restore --staged .

git add services/course/src/help.ts services/course/test/help.test.ts
git commit -m "course: helpRequestFrom() checks and builds a help request"

git add -p services/course/src/app.ts services/course/test/app.test.ts
git commit -m "course: POST /help answers 202 and publishes help.requested"

git add tests/system/stp-19-help.spec.ts docs/SYSTEM-TESTS.md
git commit -m "system: STP-19 a student asks for help and the teacher sees it"

git rebase --exec "npm test" origin/main   # every commit passes alone
git push --force-with-lease
